# X verification contract for the Go service

The frontend is complete against the following small HTTP contract. OAuth remains server-side: the browser never receives the X client secret or access token.

## Recommended X app configuration

Use OAuth 2.0 Authorization Code with PKCE and request only:

```text
users.read tweet.read offline.access
```

`tweet.read` is commonly required by X OAuth even when only `/2/users/me` is used. If refresh is unnecessary, omit `offline.access`. Configure these callbacks exactly:

```text
http://localhost:3000/auth/x/callback
https://faucet.florin.so/auth/x/callback
```

## Endpoints expected by Next.js

All three live on `FAUCET_GRAPH_URL`. JSON errors should use `{ "error": "human-readable message" }`.

### `GET /auth/x/start`

Query:

- `redirectUri`: callback URI generated by the frontend.
- `returnTo`: validated local path, normally `/`.

Generate a cryptographically random `state` and PKCE verifier/challenge. Store the state, verifier, return path, and a short expiry in a signed/encrypted HttpOnly cookie or server-side store. Return either:

```json
{ "authorizationUrl": "https://x.com/i/oauth2/authorize?..." }
```

or a 302 whose `Location` is that URL. The Next route supports both. The response's `Set-Cookie` is relayed to the browser.

### `POST /auth/x/callback`

Input from the Next callback page:

```json
{
  "code": "one-time-code-from-x",
  "state": "state-from-x",
  "redirectUri": "https://faucet.florin.so/auth/x/callback"
}
```

The Go handler must:

1. Compare `state` in constant time with the stored, single-use state.
2. Check expiry and consume the state before exchanging the code.
3. Exchange `code` using the stored PKCE verifier and the exact `redirectUri`.
4. Call `GET https://api.x.com/2/users/me` (or the current X API equivalent).
5. Store immutable X user ID plus current username in a signed server session.
6. Set a cookie such as `florin_x_session` with `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400`.
7. Return:

```json
{ "authenticated": true, "handle": "alice", "returnTo": "/" }
```

Do not trust a handle supplied by the browser as proof of ownership. Persist and rate-limit by X user ID; usernames can change.

### `GET /auth/x/session`

Read the session cookie and return one of:

```json
{ "authenticated": true, "handle": "alice" }
```

```json
{ "authenticated": false }
```

### `DELETE /auth/x/session`

Invalidate the server session, expire its cookie, and return:

```json
{ "authenticated": false }
```

## GraphQL authorization rule

The current schema is supported unchanged:

```graphql
requestToken(xHandle: String!, recipientAddress: String!, turnstileToken: String!): Boolean!
```

For safety, the resolver/middleware should load the verified X session from the forwarded cookie and reject unauthenticated requests or an `xHandle` that does not match the verified session. Better still, treat the argument as display-only and use the session's immutable X user ID as the authoritative identity.

Suggested future result type, if you want stable frontend error handling and a transaction link:

```graphql
type FaucetClaim {
  accepted: Boolean!
  transactionHash: String
  nextEligibleAt: String
}

type Mutation {
  requestToken(
    recipientAddress: String!
    turnstileToken: String!
  ): FaucetClaim!
}
```

Removing `xHandle` prevents identity spoofing at the schema boundary. The frontend currently uses the existing Boolean mutation and needs no schema change.

## Turnstile

Verify `turnstileToken` in Go with Cloudflare's Siteverify endpoint and `SPN_TURNSTILE_SECRET`. Send the request IP as `remoteip` when available. Tokens are single-use and expire quickly, so verify immediately before transfer. Never trust client-side widget success alone.

Recommended order inside the claim operation:

1. Authenticate X session.
2. Normalize/check EVM address (including zero-address rejection).
3. Verify Turnstile once.
4. Begin DB transaction and enforce both recipient/day and X-user/day uniqueness.
5. Send or enqueue the transfer idempotently.
6. Store transaction hash and commit.

Normalize recipient addresses before the daily uniqueness check. The existing `CHAR(42)` index can otherwise treat case variants as different addresses. Use a fixed UTC day boundary or return `nextEligibleAt` so "once a day" is unambiguous.

## Cookie/proxy detail

The browser talks only to `faucet.florin.so/api/...`. Next forwards its incoming `Cookie` to `faucet-graph.florin.so` and relays `Set-Cookie` back. This avoids public GraphQL CORS configuration and allows local development. Restrict the Go OAuth endpoints to expected `redirectUri` values; never accept an arbitrary callback supplied by a client.
